## 1. Bundle identifiers

| Platform | Identifier | Notes |
|---|---|---|
| Standalone (Windows/Mac/Linux) | `com.FrogletGames.CosmicShore` | Since 2026-09-11 (`BUILD_AND_DELIVERY.md` §6) |
| Android | `com.FrogletGames.CosmicShore` | Was `com.FrogletGames.TailGlider` until 2026-10-02 |
| iOS | **`com.FrogletGames.CosmicShore.dev`** | The **TEST** id. Was `com.FrogletGames.Tail-Glider` until 2026-10-02 |
| iOS (production, not yet used) | `com.FrogletGames.CosmicShore` | Flip to this when Froglet's **paid** Apple team ships TestFlight/App Store builds |

### Why iOS is on a test id

An App ID is **globally unique across every Apple team**. A free Apple ID ("Personal Team") that
builds `com.FrogletGames.CosmicShore` registers that identifier to the personal team, and Froglet's
paid team then gets *"the app identifier cannot be registered to your development team because it
is not available"* until the personal registration lapses. Testing on `.dev` keeps the production
id clean. It also lets a dev build and a store build sit side by side on one phone.

To go to production: Player Settings → iOS → Bundle Identifier → `com.FrogletGames.CosmicShore`
(it is `applicationIdentifier.iPhone` in `ProjectSettings/ProjectSettings.asset`).

### What the change costs (stated, not hidden)

- **The existing public TestFlight** (`README.md` links `testflight.apple.com/join/9ReKxeGf`) is an
  App Store Connect record bound to the OLD id. Builds with the new id cannot be uploaded to it. A
  new App Store Connect app record is needed, and testers have to re-join.
- **Android installs from itch.io** will not upgrade in place. The new package installs next to
  the old one, which can be uninstalled. Local PlayerPrefs do not carry across. Cloud Save does
  not either, because auth is UGS **anonymous** — a new install is already a new player.
- `ProjectSettings/AndroidResolverDependencies.xml` carries the Android id too. It is generated by
  the External Dependency Manager and was updated to match. The next resolve rewrites it anyway.

## 2. Getting a build onto an iPhone from a Windows machine

Unity on Windows can **export** the Xcode project but cannot **compile or sign** it. That step
needs Xcode, which only runs on macOS. Every path below is "do the Xcode step on a Mac somewhere".

### Path A — free Apple ID + one MacinCloud day + Sideloadly (no paid membership)

Constraint: **a cloud Mac cannot see your phone.** MacinCloud is a remote desktop, so Xcode's
**Run** button cannot install over USB. A free team also cannot register a device except by
plugging it into Xcode. So the cloud Mac only **compiles an unsigned app**. Signing and installing
happen on Windows, with your free Apple ID.

1. **Windows, Unity 6000.3.17f1:**
   1. Unity Hub → Installs → ⚙ → Add modules → **iOS Build Support**.
   2. File → Build Profiles → iOS → **Switch Platform**. This re-imports the whole project; consider
      a separate clone so your Windows working copy does not flip back and forth.
   3. Tick **Development Build**. That also exempts the build from `UnityPipelineReleaseGuard`.
   4. **Build** to an empty folder.
2. Zip that folder and upload it to Dropbox, OneDrive or Google Drive (MacinCloud syncs with all three).
3. **MacinCloud** (the $4/day pay-as-you-go plan is enough):
   1. Download and unzip the folder.
   2. Confirm the server's Xcode version is one Unity 6000.3 supports (Unity's iOS requirements
      page lists it).
   3. In Terminal, inside the folder:
      ```
      xcodebuild -project Unity-iPhone.xcodeproj -scheme Unity-iPhone -configuration Release \
        -sdk iphoneos -destination 'generic/platform=iOS' -derivedDataPath build \
        CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO build
      mkdir Payload
      cp -R build/Build/Products/Release-iphoneos/*.app Payload/
      zip -r CosmicShore-dev.ipa Payload
      ```
   4. Upload `CosmicShore-dev.ipa` back to the cloud drive.
4. **Windows:**
   1. Install **iTunes and iCloud from apple.com**, not the Microsoft Store versions — Sideloadly
      needs the desktop ones. Then install **Sideloadly**.
   2. Plug in the phone and trust the PC.
   3. In Sideloadly, pick the `.ipa`, sign in with the free Apple ID, and press Start.
      Sideloadly is a third-party tool that asks for that Apple ID's password, so use a dedicated
      test Apple ID, not a Froglet account.
5. **iPhone:**
   1. Settings → Privacy & Security → **Developer Mode** on (iOS 16+), then restart.
   2. Settings → General → VPN & Device Management → trust the Apple ID.

**Free-account limits:**
- The install expires after **7 days**. Re-run step 4 with the same `.ipa`; no Mac needed.
- At most 3 sideloaded apps at once.
- No TestFlight.
- No push, Game Center or In-App Purchase capabilities. Push is already off in
  `ProjectSettings/NotificationsSettings.asset`. If Xcode or Sideloadly complains about an
  In-App Purchase entitlement (`com.unity.purchasing` is installed), remove that capability for
  the test build.

### Path B — Unity Build Automation (needs the paid Apple Developer Program, $99/yr)

This is how to stop renting a Mac. Unity's Macs build the `.ipa`, but they need a signing
**certificate (.p12) and provisioning profile**, which only a paid team can create in the developer
portal. A free team's Xcode-made profile expires weekly, so it cannot drive automation.

1. **Certificate on Windows with OpenSSL** (bundled with Git for Windows):
   ```
   openssl genrsa -out ios.key 2048
   openssl req -new -key ios.key -out ios.csr -subj "/emailAddress=you@froglet.studio/CN=Name/C=US"
   ```
   Upload `ios.csr` at developer.apple.com → Certificates. Pick **Apple Development**, or
   **Apple Distribution** for TestFlight. Download the `.cer`, then:
   ```
   openssl x509 -in cert.cer -inform DER -out cert.pem -outform PEM
   openssl pkcs12 -export -legacy -inkey ios.key -in cert.pem -out ios.p12
   ```
   Keep `-legacy`. OpenSSL 3's default encryption produces `.p12` files Apple/Unity tooling rejects.
2. **App ID** `com.FrogletGames.CosmicShore.dev` (or the production id).
3. **Provisioning profile:**
   - *Development* — register the phone's UDID under Devices first. The **Apple Devices** app on
     Windows shows the UDID when you click the serial number.
   - *App Store* — for TestFlight.
4. **Unity Cloud → Build Automation:** add an iOS target on the branch, upload the `.p12` and
   `.mobileprovision`, and build.
5. **Install:**
   - A development build installs from the build's share link opened in Safari on the phone.
   - An App Store build can be uploaded to TestFlight by Build Automation directly.

A project-owned GitHub Actions macOS job is the other way off a rented Mac. It still needs the same
paid-team credentials to produce an installable build, and macOS runner minutes are billed at 10× on
private repos.

## 3. Cross-platform multiplayer (iOS ↔ Android ↔ Windows)

**Supported by the architecture, untested on real devices.** Nothing in the networking layer knows
which platform it runs on:

- **Transport is UGS Relay over UDP/DTLS.** `MultiplayerSetup` and `PartySessionService` both
  create sessions `.WithRelayNetwork()`, and that transport runs on iOS, Android and desktop alike.
  WebGL is the exception: it needs WebSockets and is not a target.
- **No networked script is platform-conditional.** Measured: none of the `NetworkBehaviour` /
  `NetworkVariable` / RPC files contains an `#if UNITY_IOS / UNITY_ANDROID / UNITY_STANDALONE`.
  So every platform serialises the same network layout.
- **Matchmaking, presence and friends ignore platform.** Session queries filter only on game mode
  and max players. The presence lobby and Friends are UGS services keyed on player id.
- **The scripting backend is the same everywhere.** iOS is always IL2CPP, and Android and
  Standalone are authored as IL2CPP too.

Three things to hold to and test:

1. **Every device must run a build from the same commit.** Nothing checks versions: sessions are
   not filtered on `Application.version` and connection approval does not compare builds. A stale
   build can join and then fail on mismatched network prefabs or RPCs. Follow-up worth doing: add
   the build version as a session property filter and a connection-approval check.
2. **All builds must use the same UGS project and environment.** They do by default, since they
   come from one repo.
3. **Seed-generated geometry across CPU architectures.** SkimRace builds its track from a shared
   seed (`SegmentSpawner`, `Random.InitState`) plus trigonometry. An ARM iPhone and an x64 PC can
   disagree in the last bits of `Sin`/`Cos`. Switchback broadcasts its course instead of a seed for
   exactly this reason (`CLAUDE.md`, Switchback). **First cross-platform test: SkimRace with an
   iPhone and a Windows PC in one match — do the tracks line up?**
