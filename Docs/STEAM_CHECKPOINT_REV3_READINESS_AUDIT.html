01 Assessment

The checkpoint's central claim — zero features left to build — has held, and then some. What it did not anticipate is that the team would spend the six weeks building fifteen more game modes. The gap that matters is no longer feature work. It is that the one system the milestone's guided-progression story rests on is not in the build, and that essentially none of the new work has been validated.

Two things are worth separating, because they carry different risk. Engineering delivery ran ahead of plan. Workstream B, sized at 9.5 person-days, is largely landed as code and tooling: a scripted Windows IL2CPP pipeline, a SteamPipe uploader, offline fallback, crash reporting, four CI workflows. Workstream C's engineering half — settings, economy, dual-sink telemetry, consent — is done. The repository carries 73 build-gate scripts and 143 design documents; the discipline is real.

Validation did not run. Workstream D is 23 person-days of profiling, soak, regression, bug bash and a signed exit checklist, and there is no evidence in the repository that any of it began. The QA backlog was generated on 13 August against PRs up to #710; the repository is now at #855. It holds 64 items, of which 58 have never been run and 6 are partial, against exactly one submitted verdict in its entire history. That would be uncomfortable at the checkpoint's seven-mode scope. At nineteen modes it is the dominant risk to the milestone.

Scope note on this audit

Everything below is verified against files in the repository. Workstreams A, E and most of F are off-machine — Steamworks paperwork, capsule art, a hosted privacy policy — and cannot be audited from here; they are marked as such rather than guessed at. The git clone available to this session covers 30 Aug – 10 Sep only, so no claim is made about what landed between 31 July and 30 August from commit history; mode and system inventory is taken from the shipped assets themselves.

02 The blocking finding

The quest and progression system is not part of the build

GameModeProgressionService is a real, substantial system — 31 KB, cloud-persisted through UGSDataService.ProgressionRepo, with unlock evaluation, intensity tiers, analytics hooks and a designer-tunable config. It is also instantiated by nothing. Its only host prefab sits in a folder named MIgration_Prefabs (DELETE LATER) and is referenced by no scene, no prefab and no asset. No code path constructs it. At runtime GameModeProgressionService.Instance is null.

  1. 01The service exists only on MIgration_Prefabs (DELETE LATER)/PlayerDataService.prefab.
  2. 02That prefab's guid appears in zero scenes, prefabs or assets across Assets/.
  3. 03No AddComponent, new GameObject or Resources.Load creates it. Every consumer reads .Instance and null-guards.
  4. 04Every null-guard fails open, so the failure is invisible: the game simply behaves as if everything is unlocked.
  5. 05Independently, the authored ProgressionConfig.asset is not assigned to the service — its serialized block carries questList and gameData and no config field at all.
ArcadeExploreView:255isLocked = false for every card. The arcade is fully open.

This reframes the checkpoint's own scoping. C10 describes “a data and configuration pass on a shipped system” and C11 “test and finalise the quest and progression system end to end” — eleven person-days that both assume the system is running. It is not. Definition of Done #4, “a fresh account completes the quest chain, with unlocks and progression persisting through Cloud Save,” cannot pass in the current build under any amount of dialogue authoring.

The second defect is the one that would bite after the first is fixed, and it is worth knowing before anyone wires the service up. ProgressionConfig.asset lists thirteen always-unlocked modes; because it is unassigned the service would fall back to its built-in default of { Maelstrom } alone. Wiring the service in without also assigning that config would take the arcade from fully open to fifteen of nineteen modes permanently locked — leaving only Skim Race, Joust, Scurry and Maelstrom reachable, and hiding every mode built since the checkpoint. Three modes are missing from the authored list as well: Astro League 37, Brood Rush 38 and Scarab Scramble 43.

02.1 Quest content, separately

The designer's backlog is real but smaller than it looks, and it is not what blocks the milestone. The chain holds six quests covering four live modes — Crystal Capture, Hex Race, Joust and Wildlife Blitz — plus a Party Game entry explicitly flagged IsPlaceholder: 1 and a Vessel Hangar unlock. Against nineteen playable modes, the chain describes about a fifth of the game.

Note also that Assets/_Scripts/System/Quest/QuestSystem.cs is a separate, older prototype and should not be mistaken for the shipping system: it carries hardcoded TestQuest / TestQuest2 fields, keeps all state in memory with no persistence, has its reward grant commented out behind a TODO, and contains a loop that ignores its own iterator and always evaluates TestQuest. It is in no scene or prefab. It is dead code and a trap for the next person who greps for “quest”.

Recommendation — decouple the build from the chain

Make the quest chain a guide, not a gate, for this milestone. GameModeProgressionService already carries IsGameModeInQuestChain(mode), and the arcade view does not consult it. Having IsGameModeUnlocked return true for any mode outside the chain is a one-line change that gives the correct semantic — the chain leads a new player through four modes, and the rest of the game stays reachable — and it holds whether the chain has six quests or twenty.

That converts the designer's content from a critical-path blocker into an enhancement that can land at any time, and it lets the service be wired into the boot chain now so that Cloud Save persistence, unlock analytics and the quest track can actually be tested. The alternative — adding the three missing ids to alwaysUnlockedModes — works too, but leaves the same failure waiting for mode twenty.

06 What to do, in order

Ordered by what unblocks the most. The first three are days of work, not weeks, and two of them are independent of the designer.

  1. 01

    Decide the progression posture, then wire the service in

    Take the guide-not-gate decision in §02, wire GameModeProgressionService into the boot chain, and assign ProgressionConfig.asset. Until this lands, Cloud Save persistence, unlock analytics and the quest track are all untestable, and Definition of Done #4 is unreachable. Do not wire the service without the config — that trades an open arcade for fifteen permanently locked modes.

    Blocker
  2. 02

    Prove a Windows player reaches the menu

    QA-BUILD-WINDOWS-PLAYER is a stated P0 that has never been run. Every prior defect in that chain — the linker failure, the pause-menu crash — was invisible in the Editor. Nothing else in Workstream D means anything until this passes, and it also unblocks B7's overlay check.

    P0
  3. 03

    Regenerate the QA backlog and start the daily pass

    Run /qa-backlog so the list covers PRs #711–#855 and the nine modes added since. C8's daily all-modes session now means nineteen modes, not seven — it should start immediately rather than waiting for the bug bash, because D5 needs a seed corpus that does not currently exist.

    Critical path
  4. 04

    Re-scope D2 against the real matrix

    Load time was sized at 8.0 person-days against roughly seven modes. The matrix is now 19 modes × 4 intensities = 76 combinations. Publish the load-time target first — it is D2's actual deliverable and it does not exist yet — then measure. The benchmark tool's Load Time Insights tab already produces the attribution.

    Re-scope
  5. 05

    Finish the de-scope sweep

    Give the store, episode and purchase surfaces the deliberate coming-soon treatment C4 specifies. MenuHubButton's Locked and Unavailable states are the pattern to extend — the mechanism exists, it simply has not been applied to the commerce surfaces.

    3.0 days
  6. 06

    Write the Playtest half of the Steam runbook

    A4, A5 and A6 have no procedure behind them, and the existing runbook points at a paid release. Add the child app, Request Access queue and friend-invite configuration, and extend Tools/Steam/upload.sh to take a second appID/depot pair.

    Workstream A/B
  7. 07

    Add wave cohorting to instrumentation

    The paid-EA gate is defined to read retention and stability cohorted by invite wave. No cohort dimension exists in the analytics code today, so the gate has no data source. This is small, and it is on the critical path to the milestone after this one.

    Gate input
  8. 08

    Close the PC platform defaults and the doc drift

    Set the default resolution to 1920 × 1080, enable resizableWindow, re-point the Standalone bundle identifier off Tail-Glider, and correct the five documents in §05 — starting with publishing Revision 2 into the repository so the runbooks stop describing a paid launch.

    Low cost

The honest summary is that the milestone is not gated on building anything. It is gated on one wiring decision, one player build, and the validation pass that was scoped in July and has not begun — now against a game roughly three times the size the plan assumed. The engineering that the checkpoint said was finished really is finished, and then some; what is missing is the evidence that it works.
