Both options show the same vessel (the Brittle Star) with the same real data as the live codex.
A · Tabs (recommended)
  • The vessel's identity (hangar render, description, flight numbers) stays on the left; everything else is one of four tabs: Elements, Game Modes, Controls, Docs and changes.
  • Elements shows ONE element at a time (Charge, Mass, Space, Time chips): the ability, its button on all three devices, the full text, what the element scales and the level 5.
  • Controls has three device tabs, Controller, PC, Mobile, each grouped Fly, Modes, Weapons.
  • Why recommended: it answers "not mix up everything" most directly. Only one subject is on screen, and every subject has room for its full text.
B · Rail
  • A section rail on the left (Elements, Game Modes, Controls, Docs and changes) under a compact identity header.
  • Elements puts all four side by side, so the kit reads at a glance; each text is shortened to fit.
  • Controls is one table: actions down, devices across, with All devices / Controller / PC / Mobile to narrow it to one device.
  • Better for comparing devices or elements; the full ability text does not fit the four columns.
What the build needs
  • The page: Docs/FleetCodex/index.html gets the picked layout; the fleet matrix stays as it is.
  • New data in Tools/Build/fleet_codex.py: the Mobile tab needs each hull's touch scheme and buttons (author_touch_profiles.py / TouchControlProfiles); the Fly rows (steer, aim) come from the input strategies, per one-stick or two-stick hull. Today the codex only knows each ability's pad and key.
  • The level-5 proposals shown in A live only in vessel docs; the build either reads them from a marked table or drops the line.
  • Game Modes ladders exist only for course-based modes; other cards show the card text alone.
