# Cosmic Shore Port — Progress Report (2026-09-29)

The previous report (`PROGRESS_2026-07-10.md`) described a **hand-ported** game: 585 game files
re-typed onto a first-party engine, with its own client harness drawing approximations of the
menu. The work since then changed the approach. The port now runs **the real game**: the
unmodified `Assets/_Scripts` compile against the engine, and the real scenes, prefabs, materials,
shaders, meshes, fonts and sprites load from `Assets/`. It runs with no Unity install.

## What runs

```
export PATH=/opt/dotnet:$PATH
dotnet build Port/src/CosmicShore.Player -o <out>
COSMIC_SHORE_PROJECT=<repo root> dotnet <out>/CosmicShore.dll
```

- **Bootstrap → Authentication → Menu_Main.** The real `AppManager` DI root, the application
  state machine, the auth scene and the menu all run. Local lanes stand in for UGS: Cloud Save,
  Friends and Leaderboards persist to disk.
- **Menu_Main.** The real `ScreenSwitcher` screens, the arcade/arena/toy box hubs and the
  lava-lamp autopilot vessel. The world is Garland: flora and fauna grow through the real
  spawners, and prism mass is drawn through the real `PrismRenderService`.
- **An arcade launch.** Tested with Bloomrush: card → configure modal → READY → the host-driven
  scene load → countdown → flight with keyboard input, including the AI backfill.
- **A scripted driver for verification.** `--do "F:verb args"` supports click, move, type, key,
  hold, pad, inspect, ancestry, trails, renderers, `eval Type.Member` and `blast N`. It works with
  `--shot F:path`, `--render-from F` and `--frames N`, and runs under xvfb or headless.

## Verification

- `tests/CosmicShore.Tests` has 1,477 tests and `tests/CosmicShore.Tests.Ported` has 352. Both
  are green.
- Visual checks are scripted runs with screenshots: menu (Debug and Release), Bloomrush flight,
  blast sequence.
- Windowed runs log **0 errors**. The one exception is `Squad..ctor`, which is faithful: the
  game's own `AllCaptains` list is empty. `--headless` has no compute support, so
  `PrismRenderService` stands down and the game's strict `[PrismClock]` diagnostics fire. That is
  exactly what a Unity `-nographics` run does.

## Known gaps, in rough priority order

1. **Networking.** A single local host only. Relay, lobby and party lanes are local placeholders, so a
   party cannot span two machines.
2. **Per-frame CPU on very large worlds.** The ECS shim stores components boxed in a dictionary per
   entity, so walking 100k+ entities each frame costs tens of milliseconds before culling. A
   packed, chunked store (Unity's archetype layout) is the fix.
3. **Visual checks still owed.** The cradle drape needs an Urchin ride, and the vision band needs
   an on-screen AI. Their code paths are verified by state only.
4. **Cinemachine / missing-script components** in tool scenes are inert shims (tool scenes only).
5. **Spawn formation warning.** A warning about the cell-relative spawn ring appears in some game
   scenes.
6. *(Resolved as a build-config fact.)* The diagnostics overlay appears only in a Debug build
   (`DEVELOPMENT_BUILD`); `-c Release` is the customer-shaped player.

## Rules the port keeps

- Nothing under `Assets/` is modified. The port reads the project and nothing else.
- No Unity or third-party source is copied. Behaviour is implemented from documented contracts.
  First-party shaders and graphs are translated.
- GLSL sources must be ASCII. The driver is handed a character count, so a multi-byte character
  truncates the source. `GlProgram` rejects a non-ASCII source up front.
